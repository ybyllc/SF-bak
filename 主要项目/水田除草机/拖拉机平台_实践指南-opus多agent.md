# 拖拉机智能控制平台实践指南 - 保守可行方案

## Context (背景)

老国企需要搭建下一代电动拖拉机中控平台，团队只有1人，无RTOS经验，需要在1个月内向领导演示可工作的原型。

**现有资源:**
- STM32F401开发板 + 完整的传感器/执行器生态
- 成熟的代码库：分层架构(任务层/控制层/驱动层)，OLED菜单系统，多种传感器驱动
- 3个试用场景：水田除草机器人、旋耕机自动平衡、履带电动平台

**目标:**
- 短期(1个月)：触摸式操作面板控制拖拉机(类似OSD)
- 中期：CAN总线多节点架构型控制
- 远期：大小脑结构(Linux导航+STM32硬件控制)

**约束:**
- 必须快速出成果，可维护性优先于完美性
- 可以有技术债，但要明确标注
- 量产/合规不是当前重点

### 1.3 需要新增的代码 (最小化)

#### 文件1: `App/hsc_Lib/1_Task/scene_control.h/c` (新建)

**功能:** 3个场景的控制逻辑

**场景1 - 水田除草机器人:**
```c
// 输入: TOF距离, 陀螺仪角度
// 输出: 2个电机PWM (左右桨)
// 逻辑:
//   - 直线前进 (陀螺仪保持航向)
//   - TOF检测到障碍(<30cm) → 后退 → 转向随机角度
//   - 覆盖策略: 简单的"碰撞-转向"算法
void Scene_WeedRobot_Run(void);
```

**场景2 - 旋耕机自动平衡:**
```c
// 输入: 陀螺仪俯仰角, 耕深传感器(ADC)
// 输出: 4个电磁阀(上下左右)
// 逻辑:
//   - PID控制俯仰角 → 输出上/下电磁阀
//   - 耕深传感器 → 调整目标俯仰角
//   - 手动模式: 按键直接控制电磁阀
void Scene_TillageBalance_Run(void);
```

**场景3 - 履带遥控模式:**
```c
// 输入: PS2手柄 或 HOTRC接收器(PWM/PPM)
// 输出: 2路PWM (左右履带)
// 逻辑:
//   - 左摇杆Y轴 → 前进/后退
//   - 右摇杆X轴 → 转向
//   - 混合算法: left = throttle + turn, right = throttle - turn
void Scene_TrackRemote_Run(void);
```

**技术债标注:**
- ⚠️ 水田除草算法过于简单(随机转向)，后期需要路径规划(如弓字形覆盖)
- ⚠️ 旋耕机缺少耕深传感器驱动，当前用ADC模拟
- ⚠️ HOTRC接收器未接入，当前用PS2手柄代替

## 第二阶段方案 (3-6个月)

### 2.1 CAN总线多节点架构

**目标:** 将单片机系统扩展为分布式控制

**架构:**
```
┌──────────────┐  CAN   ┌──────────────┐  CAN   ┌──────────────┐
│  主控节点     │◄──────►│  电机节点     │◄──────►│  传感器节点   │
│  (STM32F401) │        │  (STM32F103) │        │  (STM32F103) │
│  - 菜单显示   │        │  - 4路电机    │        │  - 陀螺仪     │
│  - 决策逻辑   │        │  - PWM输出    │        │  - TOF        │
│  - CAN主站    │        │  - CAN从站    │        │  - 编码器     │
└──────────────┘        └──────────────┘        └──────────────┘
```

**需要新增:**
1. CAN驱动层 (HAL库已支持，需要应用层协议)
2. CAN协议定义 (参考CANopen或自定义)
3. 节点管理 (心跳检测/故障处理)

**复用现有代码:**
- 主控节点: 复用menu.c + scene_control.c
- 电机节点: 复用motor_tb6612.c
- 传感器节点: 复用gyro_icm.c + TOF_VL53L0X.c

**技术债偿还:**
- ✅ 解决单片机算力不足问题(分布式计算)
- ✅ 提高系统可靠性(节点故障隔离)
- ⚠️ 新增技术债: CAN总线调试复杂，需要示波器/CAN分析仪

### 2.2 触摸屏升级

**硬件更换:**
- OLED(128×64) → TFT触摸屏(320×240或480×320)
- 驱动芯片: ILI9341/ST7789 + XPT2046触摸

**软件迁移:**
- 保持菜单逻辑不变
- 显示层: OLED API → LVGL API (已有lvgl库)
- 输入层: EC11编码器 → 触摸坐标

**技术债偿还:**
- ✅ 解决屏幕太小问题
- ✅ 提升用户体验(触摸操作)

## 第三阶段方案 (6-12个月)

### 3.1 大小脑架构

**硬件平台:**
```
┌─────────────────────────────────────────┐
│  大脑 (Linux SBC)                        │
│  - RK3588/Jetson Nano/树莓派5            │
│  - ROS2导航栈                            │
│  - 视觉识别(YOLO)                        │
│  - 路径规划(A*/DWA)                      │
│  - 自动驾驶决策                          │
└─────────────────────────────────────────┘
           ↓ CAN/Ethernet
┌─────────────────────────────────────────┐
│  小脑 (STM32)                            │
│  - 实时电机控制                          │
│  - 传感器数据采集                        │
│  - 安全保护逻辑                          │
│  - 底层硬件接口                          │
└─────────────────────────────────────────┘
```

**通信方式:**
- 方案A: CAN总线 (实时性好，带宽低)
- 方案B: Ethernet (带宽高，需要实时补丁)
- 推荐: CAN(控制指令) + Ethernet(视频流/日志)

**软件栈:**
- 大脑: ROS2 + Nav2 + OpenCV/PyTorch
- 小脑: 复用现有STM32代码 + CAN通信层
- 接口: ros2_control硬件接口

**参考案例:**
- 宇树机器狗: Jetson(大脑) + 自研电机控制器(小脑)
- 波士顿动力: 实时Linux(大脑) + FPGA(小脑)

**技术债偿还:**
- ✅ 解决算力不足(Linux高性能)
- ✅ 实现自动驾驶/视觉识别
- ⚠️ 新增技术债: 系统复杂度大幅提升，需要Linux/ROS经验

## 总结

**第一阶段(1个月)核心要点:**
1. **不要重新造轮子** - 您的代码库已经很完整，只需添加场景控制逻辑
2. **优先最简单的场景** - 履带遥控(Week 1)作为保底方案
3. **可视化很重要** - OLED菜单 + 实时数据显示能大幅提升演示效果
4. **技术债要明确** - 在代码注释和文档中标注`// TODO: 技术债 - xxx`

**代码量估算:**
- 新增代码: ~500行 (scene_control.c ~300行 + menu.c新增页面 ~200行)
- 修改代码: ~50行 (app_main.c)
- 总工作量: 约80小时 (每天工作4小时 × 20天)

**成功关键:**
- 利用AI辅助编码(您已经在用)
- 每周完成一个场景并测试
- 提前录制演示视频(避免现场翻车)
