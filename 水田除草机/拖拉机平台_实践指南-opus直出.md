# 拖拉机智能控制平台实践指南

## Context（项目背景）

老国企需要搭建下一代电动拖拉机中控平台，团队只有1人，无RTOS经验，需要在1个月内完成可演示的原型向领导展示。

**现有硬件资源：**
- STM32开发板（小脑控制器）
- 传感器：串口陀螺仪、正交编码器、TOF传感器(1.5m)
- 输入设备：按键、EC11旋钮编码器、PS2手柄、433无线遥控器
- 输出设备：OLED单色屏幕(IIC)、8路PWM电机输出(TB6612驱动)
- 通信：CAN总线控制器、多个预留串口

**应用场景：**
1. 水田除草机器人（漂浮式，双电机驱动）
2. 柴油拖拉机旋耕机自动控制（电磁阀控制）
3. 300kg电动履带平台（PWM/PPM控制）

**项目目标：**
- 短期：触摸操作面板控制（类似OSD）
- 中期：多场景CAN通信架构
- 远期：大小脑架构（Linux高性能+STM32实时控制）

---

## 第一阶段方案（1个月演示版）

### 核心策略：最小可行产品(MVP)

**技术选型：**
- **不上RTOS** - 使用超级循环+状态机（技术债1）
- **聚焦单场景** - 优先完成水田除草机器人（最简单）
- **简化UI** - OLED菜单系统，不做触摸屏（技术债2）
- **预留架构** - 模块化设计，为后续CAN/RTOS留接口

#### 1.2 开发环境配置
- STM32CubeMX生成HAL库工程
- Keil/STM32CubeIDE编译环境
- ST-Link调试器配置
- 串口调试助手（115200波特率）

#### 1.3 硬件抽象层(HAL)封装
为每个外设创建统一接口：
```c
// 示例：电机驱动接口
typedef struct {
    void (*init)(void);
    void (*set_speed)(uint8_t motor_id, int16_t speed); // -100~100
    void (*stop)(uint8_t motor_id);
    void (*emergency_stop)(void);
} motor_driver_t;
```

#### 2.1 优先级排序

2. **次要功能：**
   - PS2手柄（可用433遥控器替代）
   - 编码器（水田机器人不需要）

#### 2.2 传感器数据处理
- 陀螺仪：简单互补滤波获取航向角
- TOF：中值滤波去除噪声
- 采样频率：100Hz（10ms周期）

#### 2.3 电机控制策略
- 差速转向算法（左右电机速度差）
- PWM频率：1kHz
- 软启动/软停止（防止电流冲击）

### Phase 4: 水田除草机器人逻辑（第3周后半）

#### 4.1 运动模式
**手动模式：**
- 433遥控器：前进/后退/左转/右转/停止
- 实时显示：速度、航向、障碍物距离

**自动覆盖模式：**
- 简化版"弓"字形路径
- 直线行驶N秒 → 转向90度 → 前进1米 → 转向90度 → 循环
- 参数可调：直线时长、转向角度

#### 4.2 避障逻辑
```c
if (tof_distance < threshold) {
    stop_motors();
    turn_random_angle(90~180度);
    move_forward(0.5米);
    resume_coverage_path();
}
```

#### 4.3 状态机设计
```
IDLE → MANUAL → RUNNING
  ↓      ↓         ↓
SETUP  PAUSE  OBSTACLE_AVOID
  ↓      ↓         ↓
IDLE   MANUAL   RUNNING
```

## 技术债清单（必须后期偿还）

### 🔴 高优先级技术债

**TD1: 无RTOS导致的问题**
- **现状**：超级循环，阻塞式延时，无任务优先级
- **风险**：传感器采样不及时、按键响应卡顿、无法处理复杂并发
- **偿还时机**：第二阶段引入FreeRTOS
- **工作量**：2周（任务拆分+信号量+队列）

**TD2: 无触摸屏UI**
- **现状**：OLED单色屏+旋钮，操作效率低
- **风险**：无法满足"类似OSD"的短期目标
- **偿还时机**：采购触摸屏后（推荐：4.3寸480x272 SPI屏）
- **工作量**：3周（LVGL移植+UI重构）

**TD3: 无CAN通信**
- **现状**：单机运行，无法扩展多节点
- **风险**：无法实现中期架构目标
- **偿还时机**：第二阶段多场景适配时
- **工作量**：1周（CANopen协议栈）

### 🟡 中优先级技术债

**TD4: 简化的覆盖算法**
- **现状**：固定"弓"字形，无地图记忆
- **改进方向**：SLAM算法或基于GPS的路径规划
- **偿还时机**：远期大脑(Linux)接入后

**TD5: 无电源管理**
- **现状**：未监控电池电压，无低电量保护
- **风险**：演示时突然断电
- **偿还时机**：第一阶段末尾快速补充（ADC读电压）

**TD6: 无数据记录**
- **现状**：无法回溯运行日志
- **改进方向**：SD卡存储或通过串口上传到上位机
- **偿还时机**：第二阶段

### 🟢 低优先级技术债

**TD7: 硬编码参数**
- **现状**：PID参数、速度限制等写死在代码中
- **改进方向**：EEPROM存储+运行时修改
- **偿还时机**：第二阶段

**TD8: 无OTA升级**
- **现状**：每次更新需要ST-Link连接
- **改进方向**：Bootloader+串口/CAN升级
- **偿还时机**：第三阶段

## 第二阶段规划（3个月）

### 目标：多场景适配+CAN架构

#### 2.1 引入FreeRTOS
- 任务划分：传感器采集、控制逻辑、UI显示、通信
- 优先级设置：紧急停止>控制>传感器>UI
- 资源管理：互斥锁保护共享数据

#### 2.2 CAN总线通信
- 节点定义：
  - 主控节点（STM32）：协调者
  - 旋耕机节点：接收姿态指令，控制电磁阀
  - 履带平台节点：接收运动指令，反馈状态
- 协议设计：CANopen或自定义轻量协议
- 心跳机制：检测节点掉线

#### 2.3 场景适配
**场景1：水田除草机器人**（已完成）

**场景2：旋耕机自动平衡**
- 输入：陀螺仪俯仰角、耕深传感器
- 输出：4路电磁阀（上下左右）
- 控制算法：PID闭环控制
- 手动模式：按键直接控制电磁阀

**场景3：电动履带平台**
- 输入：HOTRC接收器PPM信号
- 输出：PWM控制信号给履带电调
- 模式切换：遥控器/自主导航

#### 2.4 触摸屏UI升级
- LVGL图形库移植
- 设计界面：
  - 主页：场景选择（3个大图标）
  - 控制页：虚拟摇杆+状态显示
  - 设置页：参数调节滑块
  - 监控页：传感器数据曲线图

## 第三阶段规划（6个月）

### 目标：大小脑架构

#### 3.1 硬件升级
- **大脑**：树莓派4B/Jetson Nano（Linux）
- **小脑**：STM32（保持现有）
- **通信**：CAN总线 + 以太网（备用）

#### 3.2 功能分工
**大脑（Linux）：**
- ROS2框架
- 视觉识别（OpenCV/YOLO）
- 路径规划（A*算法）
- 自动驾驶决策
- 数据记录与分析

**小脑（STM32）：**
- 实时电机控制（1kHz）
- 传感器数据采集
- 安全监控（紧急停止）
- 执行大脑下发的运动指令

#### 3.3 通信协议
- 大脑→小脑：运动指令（速度、方向）
- 小脑→大脑：传感器数据、状态反馈
- 频率：100Hz

## 风险与应对

### 风险1：硬件故障
- **应对**：准备备用STM32开发板和关键传感器
- **预算**：500元备件费

### 风险2：算法调试耗时
- **应对**：使用仿真器先验证逻辑，减少实物测试次数
- **工具**：MATLAB/Python仿真覆盖路径

### 风险3：进度延期
- **应对**：每周五复盘进度，及时砍掉非核心功能
- **底线方案**：只保留手动控制+避障，取消自动覆盖

## 总结

这个方案的核心思想是**分阶段迭代，快速验证**：

1. **第一阶段**：用最简单的技术栈（无RTOS、无触摸屏）快速跑通一个完整场景，证明技术可行性
2. **第二阶段**：引入工程化工具（RTOS、CAN），扩展到多场景，提升可维护性
3. **第三阶段**：升级到大小脑架构，实现智能化

**关键成功因素**：
- 严格控制第一阶段范围，不贪多
- 代码模块化，为后续重构留空间
- 每周复盘，及时调整计划
- 充分利用AI工具提升开发效率

**给领导的演示重点**：
- 展示现场实物运行（最有说服力）
- 强调架构的可扩展性（不是玩具）
- 说明技术债和后续规划（显示专业性）
- 对比同类产品（如大疆农业无人机），突出成本优势
